# Фиксация архитектурных решений (ADR)

## Статус
Принято (Accepted)

## Контекст
Архитектурные решения проекта TourBooker должны документироваться, чтобы новые люди могли понимать контекст, причины и последствия принятых решений. Необходимо выбрать единый формат и стандарт именования.

## Ограничения
1. Формат файлов должен быть текстовым и легко читаемым без специализированного ПО.
2. Файлы должны поддерживать версионирование в Git.
3. Структура должна быть строгой, чтобы облегчить автоматический парсинг и генерацию индекса.
4. Необходимость явного выделения ограничений (constraints) для каждого решения.

## Решение
Мы будем использовать формат ADR. 
Файлы будут храниться в директории `/docs/ADR/` и именоваться по шаблону `0X-<название>.md`.

Структура файла:
1. Заголовок (H1)
2. Статус (Предложено / Принято / Устарело / Отклонено)
3. Контекст (Проблема и бизнес-требования)
4. Ограничения (Технические, бизнес, временные)
5. Решение (Что именно мы выбрали и почему)
6. Последствия (Плюсы, минусы и риски)

## Последствия
- Команда получает единый источник истины по архитектуре.
- История изменений архитектуры сохраняется в Git.
- Явное указание ограничений снижает риск принятия необоснованных решений.
