# Выбор основной СУБД для хранения данных

## Статус
Принято (Accepted)

## Контекст
Системе необходимо хранить данные о пользователях, турах, бронированиях, отзывах и финансовых транзакциях. Требуется выбрать основную реляционную БД.

## Ограничения
1. **ACID-транзакции:** Критически важно исключить двойное бронирование одного и того же места в туре.
2. **Сложные связи:** Данные имеют непростую реляционную структуру (Турист -> Бронирования -> Туры -> Туроператоры).
3. **Масштабируемость чтения:** Возможность репликации для разделения нагрузок чтения и записи.
4. **Поддержка JSON:** Необходимость хранения гибких метаданных туров (например, разные визовые требования для разных стран).

## Решение
Использовать **PostgreSQL** в качестве основной СУБД.

## Последствия
- **Плюсы:** Полная поддержка ACID, надежная блокировка строк для предотвращения овербукинга; отличная работа с JSONB для гибких атрибутов туров; мощная экосистема.
- **Минусы:** Требует тщательного проектирования схемы и индексов; вертикальное масштабирование сложнее, чем у NoSQL.
- **Риски:** При неправильной настройке пула соединений может стать узким местом при пиковых нагрузках.
