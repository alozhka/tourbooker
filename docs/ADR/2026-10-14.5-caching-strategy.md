# Стратегия кэширования для повышения производительности

## Статус
Принято (Accepted)

## Контекст
Карточки туров, списки популярных направлений и данные о туроператорах читаются в сотни раз чаще, чем обновляются. Необходимо снизить нагрузку на БД и ускорить отклик API.

## Ограничения
1. **Актуальность данных:** Цена и наличие мест должны обновляться почти мгновенно после изменения туроператором.
2. **Нагрузка:** Кэш должен выдерживать резкие всплески трафика (эффект "распродажи").
3. **Сброс кэша:** Необходим механизм точечной инвалидации кэша при обновлении конкретного тура.

## Решение
Использовать **Redis** в качестве распределенного кэша.

## Последствия
- **Плюсы:** Значительное снижение нагрузки на PostgreSQL; время отклика API для чтения падает до 10-20 мс; защита БД от DDoS-подобных всплесков трафика.
- **Минусы:** Усложнение кода (необходимость прописывать логику инвалидации); Redis хранит данные в RAM, что требует выделения дополнительных ресурсов.
- **Риски:** Кэш-шторм (cache stampede) при одновременном истечении TTL. Решается использованием мьютексов или probabilistic early expiration.
